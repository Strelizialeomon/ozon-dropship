# 交接手册

> **这份给谁看**：接手的你——不写代码，但要能自己把这个系统推上线、日常用起来、再把下一步的活交代出去。
> 技术细节一律链出去（设计看[总纲](specs/spec-fulfillment-hub.md)，安装命令看 [deploy/install.md](../deploy/install.md)），正文不复述。
> 读完这份，你应该能独立走完：看懂是什么 → 知道到哪了 → 会操作 → 知道怎么把 S2 交代出去。

## 1. 这个系统是什么

你在 Ozon 上开着 10 多家店，一天出 200～1000 单。每一单背后其实是**同一套跑腿动作**：

> 看一眼客人买的是什么 → 跑去中国的批发平台下单 → 让批发商把货发到一个中转仓 →
> 仓里点收、重新打包、贴上国际快递单 → 交给干线发走 → 回头把快递单号填回 Ozon 后台。

这套跑腿以前全靠人一单一单搬，一天几百单就是几百遍。**这个系统（正式名字叫「履约中台」）就是把这条跑腿路线变成程序**：Ozon 来了新单，它自动接住、自动生成采购单、自动盯着中转仓收货、该回传单号的时候自动回传。人只在几个「该你拍板」的地方点一下。

整个项目分四步走（内部叫「波次」，就是排期批次）：

| 波次 | 干什么 | 现在 |
|---|---|---|
| **S1** | 地基 + 一家店的完整闭环 | ✅ 代码已写完、已合并 |
| **S2** | 多店规模化 + 1688 全自动下单 | ⬜ 下一步要做的（见 §6） |
| **S3** | 物流轨迹自动更新 + 退货处理 | ⬜ 没开工 |
| **S4** | 财务对账 + 商品采集上架 | ⬜ 没开工 |

| 备份 / 恢复演练 | 备份＝每天把数据另存一份；恢复演练＝**真的**拿备份在另一台机器上还原一次，验证备份是能用的 |
| 白屏 | 网页打开后一片空白，什么内容都不显示——就是系统坏了的意思 |
| L2 | 1688 给买家账号评的等级。要到 L2 以上才能申请「买家自用版」权限 |
| GMV | 成交总额。1688 申请白名单时会问我们的 GMV 有多少 |
| 出口 IP | 我们这台服务器对外的那个网络地址。Ozon 会把 key 绑到它上面，换机器要重新绑 |
| 中转点 | 货从批发商发出后先到的一个中间仓库：收货、重新打包、贴国际快递单，再交给干线发走。也叫中转仓 |
| 货代仓 / 自有仓 | 中转点的两种：货代仓是第三方物流公司提供的仓，自有仓是我们自己租的仓 |
| 线路 | 服务器到 Ozon / 1688 之间的网络通路。线路不好，接口会慢或断，所以上线前要实测 |
| 公网 IP / 域名 | 服务器在互联网上的门牌号（IP）和一个好记的名字（域名，比如 `hub.example.com`） |
| 第 152 号联邦法 | 俄罗斯的个人数据保护法，管我们把客户信息存在哪里、怎么存。上线前要咨询律师 |
| MySQL | 存数据的软件。订单、店铺、映射这些全都存在里面 |
| Redis | 排队用的软件。哪些任务该跑了、跑到哪了，由它记着 |
| Caddy | 管 HTTPS 的软件，自动申请和续期安全证书，不用人管 |
| HTTPS | 地址栏里带把小锁的那种加密连接。Ozon 要求我们的接口必须走 HTTPS |
| binlog | MySQL 的流水账，记着每一条数据是什么时候改的。有了它才能把数据恢复到「昨天下午 3 点」这种具体时刻 |
| AOF | Redis 的落盘记录。开着它，Redis 被重启或杀掉之后，排队里的任务不会丢 |
| 主密钥 | 加密所有店铺凭据的那把总钥匙。**它丢一次，所有凭据就再也解不开**，只能去各家店重新抄一遍 key |
| 数据库迁移 | 给数据库「升级结构」的动作：加个字段、加张表。每次发新版程序前要跑一遍 |
| 开机自启 | 服务器重启后程序自己起来，不用人登上去手动开 |
| 对象存储 | 云上的文件柜（比如阿里云 OSS），备份也可以传到这里而不是另一台机器 |
| 编译 | 把程序员写的代码变成能跑的程序。这一步必须有会技术的人做 |
| posting / `posting_number` | Ozon 那边对「一个订单」的编号。Ozon 的推送和接口都用它当主键，我们也拿它对账去重 |
| 采购任务 | 系统把一张 Ozon 订单翻译成「去 1688 买什么、寄到哪」之后生成的一条待办 |
| 执行器 | 干采购这活的两种方式：「人工执行器」＝人去做，「自动执行器」＝程序去做 |
| 回填 | 人工做完了，把结果（单号、付款状态）抄回系统里 |
| 人工轨道 | 新商家第一单走的路：系统做好准备，由人真的去平台点下单、付款、回填单号 |
| 备料单 | 给拼多多 / 淘宝这类没有接口的货源导出的下单清单：打印出来或照着它去平台下单，再把结果回填 |
| 交运 | 把打包好的包裹交给干线承运方——从这一刻起包裹不在我们手上了 |
| 映射 | 把「Ozon 上的这个链接」和「1688 上的这件货」对起来的那条对应关系 |
| 货源商品 / 货源平台 | 我们在 1688 等平台上卖同一件东西的进货来源；「货源商品」是它在系统里的记录 |
| 主货源 / 备货源 | 一个链接可以配两家货源：主货源优先，主货源断了自动走备货源 |
| 断货 | 货源那边这件货卖完了、下不了单了 |
| 目标库存 | 你希望这个链接显示多少库存，系统按它去同步 |
| 异常池 | 系统自己的「待办问题箱」：超时、下单失败、状态不认识……自动丢进来，等人处理 |
| 仲裁 / 表外状态 | 仲裁＝买家或平台介入的纠纷单；表外状态＝Ozon 返回了一个我们不认识的状态（出这种情况一律进异常池，等人判断） |
| 脱敏 | 敏感信息只显示头尾几位，中间打码——所以你在页面上看不到完整的 key |
| rFBS | 一种发货模式：货在卖家（我们）手上，我们自己发 |
| FBP | 一种发货模式：货在 Ozon 自己的仓库里，由 Ozon 代发 |
| 本土店 | 在俄罗斯本地有货、按本地商家经营的店 |
| 推送 | Ozon 有新订单时主动告诉我们（比我们定时去问快得多） |
| 备货 | 告诉 Ozon「这一单我们要发货了」，Ozon 才会生成面单。默认等货到中转点再备货，也可以按店设成提前备货 |
| 重试 / 重试用尽 | 失败的任务系统会自己再试几次；试满次数还不行，就叫「重试用尽」，要人去看 |
| 压测 | 故意造出大量订单，看系统扛不扛得住 |
| 库存同步 | 把货源的库存数量同步到 Ozon 链接上，避免超卖 |
| 免密支付 | 1688 那边预先授权，下单时不用每次输密码——S2 要做的全自动下单靠它 |
| 阈值 | 你自己设的一条线，越过了就触发动作（比如采购价涨超 10% 就暂停） |
| 告警 | 系统发现不对时主动发出来的提醒 |
| issue | 这个仓里的一张「任务卡」，每个活都对应一张。卡上挂标签说明它走到哪了 |
| 标签 | 挂在 issue 上的小标记。阶段标签（未开始 / 进行中 / 待上线 / 待验证）说明走到哪了；卡点标签（受阻 / 等拍板）说明卡在哪 |
| 交付物 | 一次要交的东西——可能是一份设计文档，也可能是一批代码 |
| 审核档位 / 过闸 | 每份交付物合并前要过的第一道关：系统摆一张卡问你「不审 / 轻审 / 重审 / 重审 + 变异」，你点哪档就走哪档；**只有你能点**（动手的人不能替你点）。不点也不卡住——默认按「不审」放行 |
| 日志 | 程序自己记的流水账，出了事第一眼看它。在服务器上敲 `journalctl -u fulfillment-hub` 就能看到 |

## 3. 现在到哪了

### 六份子项目

S1 拆成了六份，**代码全部写完并合并**，六份都挂着「待上线」：

| 子项目 | 干了什么 | 状态 |
|---|---|---|
| S1-A 后端地基 | 数据库、登录、任务队列、凭据加密这些底座 | 待上线 |
| S1-B Ozon 客户端 | 跟 Ozon 对接：拉单、回传单号、取面单 | 待上线 |
| S1-C 1688 客户端 | 跟 1688 对接：下单、查订单、查物流 | 待上线 · **受阻** |
| S1-D 履约编排 | 把「来单 → 采购 → 中转 → 发货」这条线串起来 | 待上线 |
| S1-E 前端操作台 | 那个网页界面 | 待上线 |
| S1-F 部署 | 服务器上怎么装、怎么发版、怎么备份 | 待上线 |

另有一张 S1-D 的白屏修复单（#20）也还没关。

### 唯一的阻塞项

**S1-C 挂着「受阻」**——它在等 1688 的「买家自用版」权限批下来。没批下来它也能继续开发，但真刀真枪的验证做不了。这条的「下次看」是 **2026-10-14**。

### 上线还缺的 5 件事

代码写完了不等于能上线。下面这 5 件前置（出处：[总纲 §12.1](specs/spec-fulfillment-hub.md)，**不依赖代码，越早启动越好**）：

1. **1688 开放平台权限**——企业实名；确认买家账号**等级 ≥ L2** 后申请「买家自用版」；再找 1688 跨境运营申请「跨境综合解决方案（自用）」白名单，问清 **GMV** 考核口径。**就是这一项卡着 S1-C。**
2. **Ozon 各店凭据**——收集 10+ 店的 `Client-Id` / `Api-Key`（也就是各家店的 key），记下每个 key 的到期日，绑定服务器的**出口 IP**（我们这台机器对外的那个地址）；确认每店是哪种发货模式。
3. **中转点**——确认各店用货代仓还是自有仓；问货代能不能接收面单 PDF、能不能回传签收。
4. **服务器与线路**——一台 Linux 服务器 + 固定公网 IP + 一个域名；实测到 Ozon / 1688 的线路质量。
5. **合规**——就俄罗斯第 152 号联邦法咨询律师。

## 4. 从零上线

这一节是 [deploy/install.md](../deploy/install.md) 的「人话版」——**告诉你每一步在干什么、大概多久、卡住看哪**。真敲命令时打开那份文件照着做，别照本文敲。

**总耗时：约 1.5 小时**（`install.md` 写的是「装完大约 1 小时」——那是不含最后逐条验收的估计；下表逐项加起来约 98 分钟）。

| install.md § | 在干什么（人话） | 多久 | 卡住看哪 |
|---|---|---|---|
| §0 | 备一台 Linux 服务器 + 固定公网 IP + 一个域名，把域名指向这台机器；防火墙放开 80、443、22 三个口 | 买机器 10 分钟，域名解析要等 | install.md §0 |
| §1 | 在服务器上建一个专用账号和几个目录（程序不以 root 跑） | 2 分钟 | install.md §1 |
| §2 | 装三个软件：**MySQL**（存数据）、**Redis**（排队跑任务）、**Caddy**（自动管 HTTPS 证书） | 10 分钟 | install.md §2 |
| §3 | 让 MySQL 开 binlog 并保留 30 天（为了能恢复到「昨天下午 3 点」这种时刻） | 3 分钟 | install.md §3 |
| §4 | 建数据库、建应用账号和备份账号（两个密码各自随机，别复用） | 5 分钟 | install.md §4 |
| §5 | 让 Redis 开 AOF（断电重启后队列里的任务不丢） | 3 分钟 | install.md §5 |
| §6 | **生成主密钥并离机留一份**——它加密着所有店铺凭据。**这一步最容易出事**：密钥只留在服务器上，机器一换/一重装，旧凭据就再也解不开了，只能重新去各店抄一遍 key | 10 分钟 | install.md §6 |
| §7 | 把后端程序编好、传上去、配好、跑数据库迁移 | 15 分钟 | install.md §7 |
| §8 | 让程序开机自启，并核验「主密钥没进环境变量、也没进进程参数」 | 5 分钟 | install.md §8 |
| **额外** | **建第一个登录账号**——系统没有自助注册，必须用一条命令建。**install.md 里没有这一步**，做法见本节末尾 | 5 分钟 | 见下方说明 |
| §9、§10 | 配好 HTTPS，把网页界面传上去 | 10 分钟 | install.md §9、§10 |
| §11 | 配好每天自动备份（另传一台机器或对象存储） | 10 分钟 | install.md §11 |
| §12 | 照验收清单逐条验一遍 | 20 分钟 | install.md §12 |

**第 6 步单独再强调一次**：主密钥生成后，把那份文本**抄进密码管理器**。这不是「最好做」，是「不做就等着丢数据」。

**「额外」那步单独说**：程序起来之后打开网页会发现**没有账号能登进去**——系统不做自助注册，第一个账号得用仓库里的 `backend/cmd/createuser` 建：

```bash
go run ./cmd/createuser -name admin -role admin   # 密码会交互式提示你输，不留命令行历史
```

**这一步 `deploy/install.md` 没写**（缺口已记在 [issue #26](https://github.com/Strelizialeomon/ozon-dropship/issues/26)）。机器上得有仓库代码和 Go 环境才跑得起来，所以和下面第 7 步一样，交给会技术的人做。

**这一步谁做**：第 7 步（编译后端）、上面那步（建账号）和整个流程都需要会敲命令行的人。你不写代码也没关系——把 [deploy/install.md](../deploy/install.md) 整份交给一个会的人或交给 AI，照着做即可。你要把关的是：第 0 步的东西买齐了没、第 6 步的密钥存好了没、第 12 步验收全过了没、以及**你自己能登进网页**。

## 5. 日常怎么用

日常就在**操作台**上（把网页界面部署完之后，用域名打开那个网页）。左边栏 7 个页面（**管理员账号还会多一条「队列监控」外链**，见「系统状态」那节），按你一天会碰到的顺序说：

### 订单工作台

Ozon 拉回来的订单全在这儿（Ozon 管一张订单叫一个 **posting**，编号就是 `posting_number`）。可以按店铺、按状态筛。看到新单进来就说明**拉单**是通的。

主要动作：勾选若干订单 → **批量生成采购任务**（这一步就是把 Ozon 订单翻译成「去 1688 买什么」）。

### 采购任务台

所有待采购的活都在这儿，分**自动**和**人工**两种执行器：

- **人工**：系统把活准备好，人真的去平台下单、付款，回来**记付款**、把快递单号**回填**进去。新商家的第一单按规则走人工。
  **注意**：页面上只有「转人工」按钮，**没有反向的「转自动」**——一单被转成人工之后就一直是人工，想让它回去得开发处理。这是目前的功能缺口，不是你没找到按钮。
- **自动**：系统自己下单（S2 才做完整，S1 阶段主要是人工轨道）。

这里还能出**备料单**——拼多多 / 淘宝那种没有接口的货源，导出一张单子让人去下单，再回填。

### 中转点与打包

包裹的国内段：**国内在途 → 待打包（已签收）→ 已交运**。

货到中转点、点收签收之后，从这里**打包交接**：导出清单给中转点，贴上面单，交运发走，然后把国际段单号登记回来。两类中转点（货代仓 / 自有仓）在这个页面上操作是一样的。

### 映射与报价

**这是最需要你懂业务的一页**：把 Ozon 上的商品和我们进货的**货源商品**对起来（叫**映射**），并配上采购价、境内运费。

映射是**按店、按商品**配的：同一个 Ozon 链接可以挂**多个**货源，并给它们排优先级（第一个断了自动走下一个）——不限于两个。还能设**目标库存**。货源状态分在售 / 断货 / 失效。

### 异常池

**出问题的地方都汇总在这一页**：超时、下单失败、停滞、仲裁、表外状态……系统自动把有问题的东西丢进来，同一个对象同一个原因只留一条（不会刷屏）。

处理完点「标记已处理」。**这一页是你每天要看的**——它是「系统替你扛不住的那些事」。

### 店铺与凭据

10+ 店的接入信息和密钥。密钥**只显示脱敏尾号**，看不到全的（安全考虑）。

每店要配：模式（**rFBS** 是自己发货、**FBP** 是 Ozon 仓发货、**本土店**是在俄罗斯本地有货）、币种、**推送**开没开（Ozon 主动推新单过来，比定时去问快）、要不要**提前备货**。

### 系统状态

你的「仪表盘」：各店最近一次同步成功是什么时候（超 30 分钟会标出来）、任务队列待处理 / 执行中 / 重试中 / 失败各多少、以及**重试用尽**的失败任务——这里能看到错误原文。

**这一页只看，不能在这里重试。** 要真把失败任务重新跑一遍，点「任务队列」卡片右上角的**「队列监控」**按钮（**只有管理员账号看得见**）——那是任务系统的后台面板，能在里面找到那条任务点重试。**每天扫一眼这一页 + 异常池**，就掌握了系统的健康状况。

## 6. S2 要做什么

S2 的目标一句话：**从「一家店能跑」变成「十几家店跑得动、采购也不用人工」**。

照[总纲 §9](specs/spec-fulfillment-hub.md) 的验收清单翻成人话，S2 干完要满足：

1. **扛得住量**：10+ 家店同时跑 7 天不出大故障；按一天 1000 单压测能过。
2. **接入 FBP 店**：这类店的货在 Ozon 自己的仓里，系统只同步状态和账，**不生成逐单采购、也不走中转点**。
3. **接上 Ozon 推送**：Ozon 会把新订单消息推给我们，**从消息到达我们这边算起 1 分钟内**入库（注意口径：Ozon 那边**发出**消息本身可能有延迟，这 1 分钟不含那段）；推送万一延迟或丢了，靠定时去问兜底（开推送的店最迟 30 分钟）；推送断 1 小时也不会漏单；1688 那边消息乱序到达时，状态不会往回退。
4. **库存同步**：货源断货 → 对应 Ozon 链接的库存 **15 分钟内**变成 0；货回来了自动写回。
5. **1688 免密支付自动下单**：成功率达到 95% 以上，失败的**全部进异常池**等人处理（不静默失败）。
6. **采购价上涨超阈值自动暂停并告警**：价格涨太多不能闷头下单，先停下来告诉你。
7. **杀掉 Redis 再重启，任务不丢**（队列有持久化 + 补投扫描兜底）。

**怎么算干完了**：上面 7 条逐条验过。验收标准全文在[总纲 §9](specs/spec-fulfillment-hub.md)。

## 7. 活怎么交代出去

你不写代码，但后面 S2、S3、S4 的活得有交代。这个仓有一套固定流程，你只要记住**四件事**：

**① 需求怎么描述。** 别直接说「帮我做 S2」。说清楚三样：**要解决什么麻烦**（现在哪儿疼）、**做成什么样算好**、**有什么不能碰的**。其余的技术选择交给做事的人提方案、你来拍板。

**② issue 怎么用。** 每个活都对应一个 [issue](https://github.com/Strelizialeomon/ozon-dropship/issues)（就是一张任务卡）。卡上挂**状态标签**，想知道某件事卡在哪，看标签就行：

- 阶段：**未开始 → 进行中 → 待上线 → 待验证**（这个仓没有测试环境，所以合并后直接进「待上线」）
- 卡点：**受阻**（等外部条件）、**等拍板**（等你做决定）

卡在「等你拍板」的单子，你不点它就不动——**看到这个标签就是找你的**。

**③ 合并前要谁点头。** 每一份交付物在合进主干**之前**，都会先摆一张「审核档位卡」问你：**不审 / 轻审 / 重审 / 重审 + 变异**。

- 你点哪档就走哪档。
- **动手的人不能替你点**——这是硬规矩，防的是「自己给自己盖章」。
- 但你不点也不会卡住：**默认按「不审」放行**。所以想审就得点，不点等于放行。

**④ 去哪看进度。** 看这一页：<https://github.com/Strelizialeomon/ozon-dropship/issues>。想更细地看某件事走到哪了，点开对应的 issue 看评论。

> 完整的流程规则（两段流程、什么算交付物、什么时候开 issue）写在 [AGENTS.md](../AGENTS.md)，本节只是给你一张流程图。

## 8. 出了事怎么办

| 出什么事 | 你会看到什么 | 先做什么 |
|---|---|---|
| **店铺凭据要过期** | 到期前 14 / 7 / 1 天会告警 | 去对应店铺的后台把 key 续上，更新到「店铺与凭据」页 |
| **某个店不同步了** | 「系统状态」页该店显示「超 30 分钟」 | 看「异常池」有没有对应条目；再不行看服务器日志（下条） |
| **有一批任务反复失败** | 「系统状态」页的「失败任务（重试用尽）」 | 看错误原文；要重试走同一页「任务队列」卡片右上角的「队列监控」按钮（**管理员账号才有**），在那里可以重试单条任务 |
| **要看日志** | 服务器上敲 `journalctl -u fulfillment-hub -n 200 --no-pager` | 备份任务的日志把 `fulfillment-hub` 换成 `fulfillment-hub-backup` |
| **要恢复数据** | — | **照 [deploy/backup/restore-drill.md](../deploy/backup/restore-drill.md) 走**，别自己想办法。备份每天自动跑（数据库全量 + binlog 保留 30 天，能恢复到任意时刻），每月要做一次恢复演练——**演练不是走形式，不演练等于没有备份** |
| **服务器整个没了** | — | 有主密钥的离机备份（§4 第 6 步）+ 备份数据，能在新机器上重建。**两样缺一不可** |

日常发布新版本、出问题要回滚：照 [deploy/release.md](../deploy/release.md) 走。
