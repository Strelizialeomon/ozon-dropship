# ADR-20261008-public-docs-boundary：公开仓文档分两层，门面与入口文档按对外口径写

- 状态：生效中
- 日期：2026-10-08
- 决策人：用户（owner）
- 适用范围：本仓文档的对外叙述口径（门面 / 入口层 vs 工作文档层）
- 取代：无
- 被取代：无
- 决策来源：2026-10-08 会话（owner 点选范围「门面 + 入口文档」；机制卡点「全要」）

## 决定

公开仓文档分两层，各按各的口径写：

- **门面与入口层**（`README.md`、`CONTRIBUTING.md`、`SECURITY.md`、`docs/handover.md`、`deploy/**`、`backend/ARCHITECTURE.md`、`frontend/README.md`——凡访客会读到的对外文档）：按**对外口径**写，**三不写**——
  1. 业务规模情报（店铺数量、订单量、GMV 等「我们」的实测数字）；
  2. 内部决策过程与角色（谁拍板、内部评审记录）；
  3. 在途状态与内部追踪号（issue 号、「受阻」、「下次看」日期、正在申请的事项）。
  **泛写规则**：产品面向的规模可写（「多店、批量订单」），「我们 / 你」的规模不写。
- **工作文档层**（`docs/specs/`、`docs/decisions/`、`AGENTS.md`）：保留内部叙述（决策人、审核留痕、业务数字）——它们是项目留痕与协作记录，本仓整体公开（[ADR-20261007-open-source](2026-10-07-open-source.md)）。

新增文档按所在层默认口径写；判不准时问 owner。

## 依据

- 2026-10-08 实测：仓库已公开（`gh repo view`：`visibility=PUBLIC`）；门面与入口文档混着内部叙述——README「前因后果」（10 多家店 / 日出 200～1000 单 / owner 拍板）、`docs/handover.md` 全篇（写给「接手的你」，含在途状态与 issue 号）、`deploy/**`「owner 点头」等。
- 同类问题已犯过一次：`docs/handover.md` 按「给接手的自己人」写，进公开仓后口吻全错位——缺的不是一次清理，而是一条可判的线。
- owner 2026-10-08 点选：本轮只改门面 + 入口层；工作文档层不动（改它伤决策追溯价值，收益小）。

## 否决了什么

- **只公开代码、把内部文档移出公开仓**：[ADR-20261007-open-source](2026-10-07-open-source.md) 已否决过（双仓维护 + 全量链接重写），本轮重申不采用。
- **连工作文档层一起去内部化**：决策来源与审核留痕正是其本体，改掉等于销毁记录。
- **只做一次性清理、不立成文口径**：同类内容会重新漏进来，owner 反复纠。

## 接受的代价

- 同一信息可能存在「两层两种写法」的重复叙述与维护成本；写文档要先判层。
- 工作文档层仍含业务规模与决策记录（owner 2026-10-07 已知悉并接受）。
- 泛写削弱部分文案的具体感（如压测目标由「一天 1000 单」改为「目标单量」）。

## 允许重开的条件

- 项目形态变化（转为纯开源产品、无自营业务）→ 对外口径可放宽或两层合一。
- owner 改变公开策略（如重新收紧可见性）→ 走取代。
