## 2. 背景与现状

2026-10-08 owner 反馈：「我们的项目都开源了，不要写这些……让他可以公开化，不要有那么多的内部描述」——指向 README「前因后果」等节把经营与内部决策叙述暴露在公开仓。owner 当场点选：范围 = **门面 + 入口文档**；工作文档层不动；机制卡点「全要」（口径线 + 新 ADR）。

**现状实测**（2026-10-08，全库扫 + `gh` 实测）：

| # | 位置 | 实证 |
|---|---|---|
| 1 | 仓库可见性 | `gh repo view`：`visibility=PUBLIC`——「公开仓」已是事实，本份让文档配得上这个事实 |
| 2 | `README.md` | 「前因后果」含 10 多家店 / 日出 200～1000 单 / ERP 评估 / owner 拍板；「现在到哪了」「怎么用起来」含在途阻塞与 5 项前置；「这个仓怎么干活」含内部角色措辞 |
| 3 | `docs/handover.md` | 全篇写给「接手的你」；开篇即 10 多家店 / 200～1000 单；§3 含受阻状态、issue 号、「下次看」日期 |
| 4 | 入口散点 | `deploy/README.md`「owner 点头后跑」「S1 父 issue」；`deploy/install.md` 5 处 S1-x 编号 + issue #11；`deploy/line-test/README.md`「owner 拍板」「贴 #5」；`frontend/README.md`「与 owner 现有项目一致」；`backend/ARCHITECTURE.md`「（S1-B / S1-C 实施）」；`SECURITY.md` S1/S2 措辞 |
| 5 | `AGENTS.md` | 复核结论：无业务情报，全为流程语言（「用户」是 agent 视角的正确称呼）——**无需改动** |

**为什么分层而不是全清**：specs / ADR 的决策来源与审核留痕正是其本体（可回溯依据），owner 已知悉并接受其公开（ADR-20261007-open-source）；缺的是「门面 / 入口」这一层可判的口径线，这次补上。

## 3. 要做的事

### 3.1 `README.md` 整份重写（公开向）

五件公开资产（英文摘要 / 徽章 / 开发者快速开始 / 参与 / 许可）原样保留；其余按下表：

| 节 | 处理 |
|---|---|
| 简介（英 + 中） | 保留定位句；中文「自用」→「自托管」；删单量暗示（「一天几百上千单全靠人手工搬」→ 去数字） |
| 能干什么（**新**） | 6–8 条泛写：Ozon 拉单与推送、采购任务（人工 / 自动双轨）、中转打包交运、单号回传、库存同步、异常池、操作台；来源 = handover §5 的泛写版，不写数字 |
| 前因后果 | **删节**；动机一句并入简介（最终措辞见 §6） |
| 现在到哪了 / 怎么用起来 | 并为「项目状态」一小节：只写「核心闭环已实现、尚未生产部署、接口可能变动」；不出现波次编号与在途申请。部署入口指 `deploy/install.md`，前置条件泛写（各平台自有凭据与权限、Linux 服务器 + 域名 + MySQL / Redis） |
| 开发者：本地跑起来 | 原样 |
| 文档地图 | 重排：设计 → `docs/specs/`；长期决定 → `docs/decisions/`；后端结构 → `backend/ARCHITECTURE.md`；部署运维 → `deploy/`；操作与上线手册 → `docs/handover.md`（中性位置，**去掉「接手的你（不写代码）」首推行**） |
| 参与 / 许可 | 原样 |
| 这个仓怎么干活 | 精简为公开口径三行：设计先行（需求 → spec → issue 实施）、长期决定记 ADR、每份交付物合并前过审核；细节链 `AGENTS.md`，不复述 |

### 3.2 `docs/handover.md` 去内部化（结构不动、功能不减）

口径：**删业务情报与在途状态；保留全部操作内容**。逐节：

| 节 | 改法 |
|---|---|
| 标题与头部 | H1「交接手册」→「操作与上线手册」（文件名 `handover.md` 不改——链稳定性）；「接手的你」→「要把这套系统推到线上并使用它的人」（保留「不写代码也能看懂」定位） |
| §1 系统是什么 | 开篇「你在 Ozon 上开着 10 多家店，一天出 200～1000 单」→ 泛写痛点（多店、日常几百上千单之后纯手工履约搬不动），不写「我们 / 你」的实测数字；S1–S4 波次表保留 |
| §2 术语表 | 去「我们的 / 你们的」所有格（我们的店 / 我们的进货渠道 / 问我们的 GMV）→ 泛写；其余条目保留 |
| §3 现在到哪了 | **整节重写为「上线前要备齐什么」**：删受阻状态、issue 号、「下次看」日期、权限申请在途；保留 5 项前置的泛写版（平台权限、店铺凭据、中转点、服务器与线路、合规）；S1-A～F 子项目表删除（结构信息由仓库 spec 承载） |
| §4 从零上线 | 保留（人话版步骤表）；删 issue #26 引用（改「该步未写入 install.md，做法见本节」） |
| §5 日常怎么用 | 保留；「10+ 店的接入信息」→「各店铺的接入信息」 |
| §6 S2 要做什么 | 保留目标清单；「10+ 家店同时跑 7 天」「一天 1000 单压测」→ 泛写（多店并发 / 按目标单量压测）；验收全文仍指总纲 §9 |
| §7 活怎么交代出去 | 保留四件事框架；去「你不写代码 / owner」类角色措辞，读者改为「要把后续开发交代出去的人」 |
| §8 出了事怎么办 | 保留 |

### 3.4 对外口径线

内容以新 ADR 为准（§3.5），要点：**两层制**（门面 / 入口层 vs 工作文档层）+ **三不写**（业务规模情报 / 内部决策过程与角色 / 在途状态与内部追踪号）+ **泛写规则**（可写产品面向的规模，不写「我们」的实测数字）。

### 3.5 新 ADR

`docs/decisions/2026-10-08-public-docs-boundary.md`（随本 PR 落；**不取代** ADR-20261007-open-source——可见性不变，只加内容口径），并机械收编进 `docs/decisions/README.md` 一览表。

### 3.6 实施与发布序

实施另开 issue、从段二进（worktree `issue-<N>`）；本 PR（spec + ADR）合并后再开 issue，正文锚本文件永久链接 + 改动面（README、handover、6 份散点 + 新 ADR + 一览表）+ 验收要点。

## 4. 机制清单

| # | 机制 | 解决什么 / 没有它会怎样 |
|---|---|---|
| 1 | 对外口径线（两层制 + 三不写 + 泛写规则） | 公开仓门面与入口文档混着内部情报；没有它：这次清完，下次写文档没有可判的线，同类内容重新漏进来，owner 反复纠 |
| 2 | `ADR-20261008-public-docs-boundary` | 别的 agent / 任务不知道这条线，会照旧把业务数字写进公开文档；没有它：同一决策被反复重拍 |

## 6. 自定细节

**口径与判据（agent 定，owner 扫一眼）**

- 红词表（验收 grep 用）：`owner`、`10 多家店`、`200～1000`、`日出单`、`受阻`、`下次看`、`issue #\d`、`S1-[A-F]`；范围 = README + handover + §3.3 六份；**允许**：「拍板」的读者视角用法（「你来拍板」）、标签名（「待上线」）、handover §1 的 S1–S4 波次表。
- 泛写规则：「我们 / 你 的规模」必删；「产品面向的规模」可写（多店、批量订单、目标单量）。
- README 简介动机句最终措辞：「为补上现成 ERP 在采购下单环节的自动化缺口」；中文「自用」→「自托管」。
- README 不设「前因后果」节；「能干什么」为新增节（6–8 条）。
- handover 标题改「操作与上线手册」；文件名 `handover.md` 不改（链稳定性优先）。
- handover §3 新标题「上线前要备齐什么」；五项前置措辞 = 总纲 §12.1 的泛写版（不复制在途与数字）。
- 本 ADR 随本 PR 收编一览表（机械回填，属豁免）；实施时复核该行仍在、未被后续合并冲掉。
- 实施 PR 回填本文头部实施单号；不改本文其余内容。
- 不动：`docs/specs/`、`docs/decisions/` 正文（除一览表）、全部代码、GitHub 仓库设置。
